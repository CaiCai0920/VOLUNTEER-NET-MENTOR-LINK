### 表 7 `vm_verifications` — 身份核验申请单 ★新增★

**为什么要有这张表？**

原来认证信息是直接写在用户档案上的，只存**当前状态**，带来四个问题：

| 问题 | 后果 |
|---|---|
| 驳回没理由 | 用户不知道为什么被拒，只能瞎猜重填 |
| 重新提交会覆盖 | 上一次交的材料没了，审核员没法比对 |
| 查不到审核人 | 出了问题没人负责 |
| 没有历史 | 统计不了"多少人被驳回过" |

新表把**每一次提交**留成一张单子：

| 字段 | 说什么 |
|---|---|
| `id` | 申请单编号 |
| `user_id` / `user_name` | 申请人 |
| `role` | 申请的身份（新生 / 学长） |
| `real_name` `student_id` `phone` `id_photo` | 提交的材料（敏感） |
| `status` | `pending` / `approved` / `rejected` |
| `reason` | **驳回理由**（审核员填，用户看得到） |
| `reviewer_id` / `reviewer_name` | 谁审的 |
| `reviewed_at` / `created_at` | 审核时间 / 提交时间 |

**两个地方的关系**，记住这一句就够了：

- `vm_verifications` = 完整的申请流水（查历史用）
- `vm_users.verify_status` = 最新结论的快照（页面显示用，读得快）

两边会自动同步，**现有页面一个字都不用改**。

## 四、三条核心逻辑（改代码前必须知道）

### 1. 在线状态：看心跳，不看开关

小程序被强杀、断网时**不会通知后台**，所以 `isOnline` 这种开关永远没人能改回「离线」——这正是当初「说过话的人全挂在上面」的根因。

正确做法：**每 15 秒上报一次 `last_active`，查询时用「距今 40 秒内」筛出在线的人。**状态是算出来的，不是存出来的。

### 2. 认领要防双抢

两个人同时点「我来答」，只能有一个成功。做法是条件更新（只认领还处于待认领状态的记录），第二个人的更新会落空。帖子和会话都这么处理了。

### 3. 同一个人有两个档案

一个人可以在「新生」和「学长」两个身份间切换，这是**两份独立档案、两个 ID**——否则他自己的消息会被判成对方发的，气泡全挤一边。切换时靠「学号 + 实名」找回对应身份下的档案。
